Overview

Executive Summary & System Architecture

Varuna Ops is a file-heavy, real-time drone operations platform. It is not a single app — it is a set of cooperating services that must each be hosted on the right kind of infrastructure. The most important architectural fact for budgeting: each drone project produces 50–100 GB of raw imagery & deliverables, so object storage (not the server or database) is the component that grows the cost over time. We host that on Cloudflare R2, which charges for storage but — critically — has zero egress fees, so clients downloading large deliverables never trigger surprise bandwidth bills.

Note on scaling the API: Today the API runs as a single instance (correct for Socket.IO without a shared adapter). To run multiple API instances behind a load balancer (Tier 3), the codebase needs the @socket.io/redis-adapter wired in — a small, well-understood change already noted in the project's own deployment comments.

Capacity Planning

Storage, Space & Usage — How Much Can It Hold?

Two very different kinds of "space" matter. The database stays small (records are tiny); the object storage is what grows, because every drone project carries tens of gigabytes of imagery and deliverables. Plan the budget around object storage.

🐘 Database (PostgreSQL) — stays small

Holds text records only: projects, users, pipeline, estimations, notifications.

  • 10 GB handles tens of thousands of projects & users comfortably
  • Typical real usage in year one: under 1–2 GB
  • Redis queue: a few hundred MB at most

☁️ Object storage (R2) — the one that grows

Holds raw drone data & deliverables. This is the real capacity question.

  • Each project ≈ 50–100 GB (the platform is built for this)
  • No hard cap — R2 bills per GB, grows infinitely
  • Egress is FREE — client downloads cost nothing

The free-egress advantage in numbers: On AWS S3, a client downloading a 100 GB project deliverable would cost ≈ $9 in egress every time. On Cloudflare R2 that download is $0. For a platform whose whole point is delivering big files to clients, this single fact can save thousands of dollars a year — which is exactly why R2 was chosen.

Execution Plan

Step-by-Step Deployment Roadmap

A clear, phased path from an empty cloud account to a live, secured production system. Total effort: roughly 5–6 working days for the recommended (Tier 2) setup.

Phase 0 — Pre-flight & accounts ~1 day
Buy the domain. Create Cloudflare, hosting, database & email accounts. Create the R2 bucket + access keys. Generate a strong JWT_SECRET. Rotate any secret ever shared. Draft the production .env (never commit it).
Phase 1 — Database ~½ day
Provision managed PostgreSQL. Run migrations (npm run migrate — all 16+). Seed the first admin user. Confirm automated backups are on.
Phase 2 — Backend API + Worker ~1 day
Deploy varuna-api and varuna-worker as two services. Set all env vars (DB, R2, Redis, SMTP). Connect Redis & R2. Verify the /health endpoint and that a test job runs on the worker.
Phase 3 — Frontend ~½ day
Set VITE_API_URL to the API domain. Build (vite build) and deploy to Cloudflare Pages. Attach the custom domain.
Phase 4 — Networking, domains & SSL ~½ day
Point DNS for app + API subdomains. Enable free TLS. Lock CORS & Socket.IO origin to your domain via FRONTEND_URL. Confirm real-time updates work end-to-end.
Phase 5 — Hardening & observability ~1 day
Set up daily DB backups, uptime monitoring (UptimeRobot), error tracking (Sentry), and email-delivery checks. Verify rate-limiting & security headers (Helmet) are active in production.
Phase 6 — Go-live & handover ~½ day
Full smoke test (login, project create, upload, export/ZIP, notifications, emails). Final DNS cutover. Hand over credentials, runbook & monitoring dashboards.

✅ Production-readiness today

The platform has been through multiple zero-bug stabilization passes — crashes fixed, migrations applied, security headers, rate-limiting, JWT auth, 2FA, RBAC and resumable uploads are all in place. Internal readiness is assessed at ~99%.

📋 Small pre-launch checklist

  • Move background jobs to live Redis (currently optional)
  • Add Socket.IO Redis adapter before multi-instance
  • Cap ZIP memory for very large projects
  • Plan Node 22 upgrade (AWS SDK, by 2027)
